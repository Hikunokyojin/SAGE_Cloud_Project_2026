# Security

SAGE accepts free-text input and lets language models act on it, so its security model is built around two ideas: **limit what any single component can do**, and **never let a model's output be the final authority**.

## Threats and defences

| Threat | Defence |
|---|---|
| Prompt injection in the user's request | **Input Guard** screens text with pattern rules before any model sees it; matched phrases are replaced with `[filtered]` and the request continues |
| An injected instruction steering later agents | Only Intent ever sees the user text (after Input Guard); every later agent receives **structured, typed data**, not raw conversation history |
| A model picking a service that breaks the user's limits | **Deterministic** selection plus an **independent Reviewer** that re-derives every mandatory constraint |
| Runaway loops and silent failure | Hard cap of 3 re-negotiation tries; every failure path ends with a human alert |
| A compromised component reaching other resources | One **least-privilege IAM role per Lambda**; no wildcard resources on any custom statement |
| Leaked credentials | No keys in the repository; secrets live in SSM Parameter Store (SecureString) or a local `.env`; no standing credentials on agents; the Conductor instance has **no SSH key and no open port 22** (SSM Session Manager only) |
| Unexplained decisions | Every agent step is recorded in DynamoDB and AWS CloudTrail logs account activity |
| Surprise cloud bill | AWS Budgets alerts at 80% of actual and 100% of forecast spend |

## IAM review (least privilege)

Every Lambda role also carries AWS's managed basic-execution policy (CloudWatch Logs for that function). Beyond that, each role is granted only what its own code calls:

| Role | Allowed actions | Scoped to |
|---|---|---|
| Input Guard, Negotiator | `dynamodb:PutItem` | the one audit table (these agents make no other calls) |
| Intent, Explainer, Escalation Explainer | `dynamodb:PutItem`, `ssm:GetParameter`, `kms:Decrypt` | the audit table; the single Groq key parameter; KMS only via the SSM service |
| Broker | `dynamodb:PutItem`, `ssm:GetParameter` | the audit table; the three named Mongo/Qdrant parameters |
| Reviewer, Unsatisfiable-escalation | `dynamodb:PutItem`, `sns:Publish` | the audit table; the one escalation topic |
| Conductor (EC2 instance role) | `lambda:InvokeFunction`; DynamoDB read; S3 read | the 8 named agent functions; the audit table (read-only); the private deploy bucket (read-only) |

The review was performed against the policies as deployed in the live account, not just the infrastructure source. It found one issue, fixed during the review: the agents' audit-write grants originally used CDK's `grantWriteData()`, which attaches `BatchWriteItem`, `UpdateItem` and `DeleteItem` as well. They were tightened to the single `PutItem` action the code actually uses.

These properties are also asserted automatically in [`infra/cdk/test/sage-stack.test.ts`](../infra/cdk/test/sage-stack.test.ts), so a regression fails `npm test`:

- Exactly 8 `sage-*` Lambda functions exist.
- No policy anywhere grants `bedrock:InvokeModel`.
- Only Intent, Explainer and Escalation Explainer can read the Groq key; only Reviewer and Unsatisfiable-escalation can publish to SNS.
- No security group opens port 22, and the Conductor role's `lambda:InvokeFunction` is not `*`.

## Prompt-injection test suite

[`agents/input-guard`](../agents/input-guard) contains a 21-case suite ([cases](../agents/input-guard/src/security/cases.ts), run by `npm test`; a readable report is generated by `npm run security-report` into [`evaluation/results/prompt-injection-report.md`](../evaluation/results/prompt-injection-report.md)):

| Category | Cases | Expected behaviour |
|---|---|---|
| Role override, delimiter injection, prompt leak (including one combined payload) | 14 | flagged and filtered |
| Benign requests that use words like "ignore" or "system" innocently | 4 | not flagged |
| **Known gaps** | 3 | **not caught, by design of a rule-based screen** |

"21/21 passing" therefore means all 21 cases behaved as documented, **not** that every attack is stopped. The three known gaps are base64-encoded payloads, full-width Unicode look-alikes, and non-English phrasing. They are recorded deliberately so the limitation is visible. Because of the design above, a missed injection can influence only the Intent step output, not later agents, and the Reviewer still checks the final choice against the user's actual limits.

## Reporting a vulnerability

Please open a private security advisory on this repository (Security tab, "Report a vulnerability") rather than a public issue. This is a research and portfolio project, not a hardened production service; do not deploy it with real secrets or sensitive data without further review.
